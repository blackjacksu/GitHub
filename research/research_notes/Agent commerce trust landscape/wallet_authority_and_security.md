## Key Question 1 — Delegation and session keys: ERC-4337, EIP-7702, ERC-7715/7710, MetaMask Delegation Toolkit, ZeroDev/Kernel, Safe modules, Coinbase Smart Wallet spend permissions / sub-accounts; what is production-ready on Base, and how each expresses caps, allowlists, time limits and revocation

### Takeaway
The on-chain primitives are now mature enough to build the consumer's "cold owner key + hot policy-bound agent key" design: EIP-7702 (Final, live on mainnet since Pectra 2025-05-07) and ERC-4337 (Final) are the account layers; ERC-7579 (Draft but widely implemented by Kernel, Safe7579, MetaMask DeleGator) is the module layer; and the actual spending-cap enforcement lives in audited, Base-deployed contracts — Coinbase `SpendPermissionManager` (recurring allowance per period with start/end and revoke by either party), MetaMask Delegation Framework caveat enforcers (ERC20/native period-transfer, streaming, allowed targets/methods, timestamp, limited calls, nonce), Zodiac Roles Modifier (role-scoped targets/functions/conditions with allowances; deployed on Base) and the Safe Allowance Module (per-delegate budget with reset interval). The RPC-level permission standards (ERC-7715/ERC-7710) are still Draft and MetaMask's implementation is Flask-only/experimental; treat them as the future interface, not the thing you depend on in October 2026.

### Cited Findings

**Standards status (all verified against the canonical EIP/ERC repositories)**
- EIP-7702 "Set Code for EOAs" — Status: Final; created 2024-05-07; adds tx type `0x04` with an `authorization_list` of `[chain_id, address, nonce, y_parity, r, s]`; sets the EOA's code to the delegation indicator `0xef0100 || address`; authorizing the zero address clears the delegation; `chain_id = 0` makes an authorization valid on every chain; per-authorization gas `PER_AUTH_BASE_COST = 12,500`, `PER_EMPTY_ACCOUNT_COST = 25,000`. — [EIP-7702 (ethereum/EIPs)](https://github.com/ethereum/EIPs/blob/master/EIPS/eip-7702.md)
- EIP-7702 security considerations: the delegate contract should implement and sign over a nonce (replay), sign over `value`, `gas`, target and calldata; storage collisions when switching delegates (recommend ERC-7201 namespaced storage); initialization can be front-run because no initcode runs, so wallets should require setup calldata signed by the EOA key; "wallets must not let applications prompt users to sign authorizations, since delegated code has unrestricted access to the account and must be audited." — [EIP-7702](https://github.com/ethereum/EIPs/blob/master/EIPS/eip-7702.md)
- Pectra (Prague/Electra) hard fork, EIP-7600 (Status: Final) — includes EIP-7702; mainnet activation epoch 364032, timestamp 1746612311 = 2025-05-07 10:05:11 UTC. — [EIP-7600 Hardfork Meta: Pectra](https://github.com/ethereum/EIPs/blob/master/EIPS/eip-7600.md)
- ERC-4337 "Account Abstraction Using Alt Mempool" — Status: Final; created 2021-09-29; requires ERC-712 and EIP-7702; singleton EntryPoint runs a verification loop (`validateUserOp`) then execution loop; 2-D nonces (192-bit key + 64-bit sequence); `validUntil`/`validAfter` time ranges on validation; staking of paymasters/factories "is never slashed"; EIP-7702 accounts "should initialize only once". — [ERC-4337 (ethereum/ERCs)](https://github.com/ethereum/ERCs/blob/master/ERCS/erc-4337.md)
- ERC-7579 "Minimal Modular Smart Accounts" — Status: Draft; created 2023-12-14; requires ERC-165, ERC-1271, ERC-2771, ERC-4337; module type IDs: Validation (1), Execution (2), Fallback (3), Hooks (4); accounts must distinguish module types so a validator cannot call `executeFromExecutor`. — [ERC-7579](https://github.com/ethereum/ERCs/blob/master/ERCS/erc-7579.md)
- ERC-7710 "Smart Contract Delegation" — Status: Draft; created 2024-05-20; authors McPeck, Finlay, Dawson, Chiang; requires ERC-1271 and ERC-7579; single interface `redeemDelegations(bytes[] permissionContexts, bytes32[] modes, bytes[] executionCallData)` which must be atomic; the spec defines no caveat/enforcer vocabulary and no revocation method ("delegations can be revoked, expire, or become invalid due to state changes"; dApps should simulate before submitting). — [ERC-7710](https://github.com/ethereum/ERCs/blob/master/ERCS/erc-7710.md)
- ERC-7715 "Request Permissions from Wallets" — Status: Draft; created 2024-05-24; requires ERC-4337 and ERC-7710; RPC methods `wallet_requestExecutionPermissions`, `wallet_revokeExecutionPermission` (takes `permissionContext`), `wallet_getSupportedExecutionPermissions`, `wallet_getGrantedExecutionPermissions`; example permission types `native-token-allowance`, `erc20-token-allowance`, `erc721-token-allowance` with an `isAdjustmentAllowed` flag; the only defined rule is `expiry`; the document itself has inconsistencies (`rulesTypes` vs `ruleTypes`). — [ERC-7715](https://github.com/ethereum/ERCs/blob/master/ERCS/erc-7715.md)
- ERC-1271 — Status: Final; created 2018-07-25; `isValidSignature(bytes32 hash, bytes signature) view returns (bytes4)`; magic value `0x1626ba7e`; no gas limit is specified so callers must not hard-code a gas amount. — [ERC-1271](https://github.com/ethereum/ERCs/blob/master/ERCS/erc-1271.md)
- ERC-8183 "Agentic Commerce" — Status: Draft; created 2026-02-25; authors Crapis (EF dAI), Lim, Tay, Chooi (Virtuals); requires ERC-20. Defines a `Job` escrow (client/provider/evaluator; states Open/Funded/Submitted/Completed/Rejected/Expired; functions `createJob, setProvider, setBudget, fund, submit, complete, reject, claimRefund`), an optional `IACPHook` with `beforeAction`/`afterAction`, and an optional ERC-2771 meta-tx extension. **It contains no delegation or session-key mechanism.** Security notes: evaluator is fully trusted post-submission; hooks are trusted, client-chosen, and a reverting hook can block actions until expiry (so `claimRefund` is non-hookable); hooks should be gas-limited and not upgradeable mid-job. — [ERC-8183](https://github.com/ethereum/ERCs/blob/master/ERCS/erc-8183.md)
- Secondary coverage says ERC-8183 was developed by Virtuals Protocol with the EF dAI team and remained "Draft as of August 3, 2026", with deployments reported on Arbitrum, BNB Chain and XRPL (search snippet; primary not fetched). — [QuickNode](https://www.quicknode.com/blog/erc-8183-agentic-commerce); [Dwellir](https://www.dwellir.com/blog/erc-8183-agentic-commerce-explained)

### Inferences
- **Production-ready on Base today (Oct 2026):** Coinbase `SpendPermissionManager` (audited 3× by Spearbit/Cantina, Base address published, used by Base Account/Sub Accounts); MetaMask Delegation Framework v1.3.0 (audited, Base mainnet address published, rich enforcer set); Zodiac Roles Modifier (audited, Base address published, used by ENS and Gnosis Pay treasuries); ERC-4337 (Final) with EntryPoint v0.6/v0.7/v0.9 and ERC-7579 accounts (Kernel v3.x; Safe7579). EIP-7702 is live at the protocol level on L1 (Pectra); Base, as an OP-Stack chain, received 7702 with the Isthmus upgrade — I could not fetch the Base/OP hardfork page to confirm the Base activation date, so treat Base 7702 activation as "very likely live, verify in superchain-registry".
- **Experimental / not to depend on:** ERC-7715 and ERC-7710 (Draft; MetaMask Flask-only; the spec lacks a revocation method and rule vocabulary); ERC-8183 (Draft, 8 months old, no session-key semantics); Kernel v4.0 (released this month, audit folder removed from repo — look for an external audit before using); Base Sub Accounts if still canary/Sepolia-only; Safe Allowance Module on Base (no visible audit/deployment for 8453 — verify in `safe-modules-deployments/src/assets/allowance-module/v0.1.1`).
- **How caps/allowlists/time limits/revocation map:** (a) Spend Permissions = one token × allowance-per-period × [start,end), revocable by owner or spender, no target allowlist (it only moves tokens to a recipient the spender chooses — the *spender contract* must enforce where funds go). (b) MetaMask delegations = composable caveats: `AllowedTargets + AllowedMethods + ERC20PeriodTransfer + Timestamp + LimitedCalls + Nonce`; revocation via `NonceEnforcer`/manager-level disable (spec says implementation-defined). (c) Zodiac Roles = role → target → selector → parameter conditions + allowances; revocation = unassign role. (d) ZeroDev = signer + {CallPolicy, RateLimitPolicy, GasPolicy, TimestampPolicy}; revocation = uninstall permission. (e) Safe Allowance Module = delegate × token × amount × reset interval; revocation = `deleteAllowance`/`removeDelegate`.
- **On the consumer's "ERC-8183 hook / session-key pattern":** ERC-8183's `IACPHook` is a pre/post-action callback on the escrow Job contract (client-chosen, trusted, can grief by reverting) — it is *not* a wallet-authorization primitive. The hot-key spending cap should be implemented at the account layer (Spend Permission to a bureau-controlled spender contract, or a DeleGator/Kernel session key with period-transfer + allowed-target caveats), and an ERC-8183 hook, if used at all, should only *additionally* check that funded Jobs match the policy. Mixing the two conflates escrow lifecycle with signing authority.
- **Owner-key = ERC-721 holder:** ERC-721 ownership is checked on-chain, so this fits naturally as the "root validator"/sudo condition in a Kernel-style account or as the `account` owner of a Coinbase Smart Wallet; none of the surveyed systems has an off-the-shelf "NFT-holder is owner" validator, so expect to write a small validator module and audit it.

## Key Question 2 — Agent-specific wallet products (Coinbase AgentKit/CDP, Crossmint, Privy, Turnkey, Thirdweb, Skyfire, Payman, Stripe) and their policy languages

### Takeaway
The hosted "agent wallet" products converge on the same shape — keys in a TEE/enclave, a declarative allow/deny rule list evaluated server-side on every signing request, default-deny — but their policy expressiveness differs: Turnkey has a real boolean policy language with `consensus`/`condition` expressions, CDP uses typed criteria (`ethValue`, `evmAddress`, `evmNetwork`, `evmData`/ABI), Privy uses rule lists with field/operator/value conditions, and Crossmint pushes limits on-chain into a smart-contract wallet. AgentKit itself enforces nothing; it relies on the CDP policy engine or framework middleware. Stripe's current agent offering is billing/metering and an OAuth MCP server, not an agent spending wallet.

### Cited Findings
- **CDP Policy Engine** (official overview, search snippet; docs blocked): rules accept or reject signing operations based on parameters like destination, value and network; embedded-wallet policies support address allowlists/denylists, transaction value caps, message-signing restrictions and network restrictions; rules evaluate in order and **if no rule matches the request is rejected (fail-secure)**; embedded-wallet policies support only project scope. — [CDP policy engine overview](https://docs.cdp.coinbase.com/wallets/security-and-policies/policy-engine/overview.md); [embedded wallet policies](https://docs.cdp.coinbase.com/embedded-wallets/policies/overview)
- Coinbase describes policies as "declarative rules enforced on every signature", definable in the CDP Portal or via TypeScript/Python SDKs, with enforcement "inside Coinbase's Trusted Execution Environment"; examples: cap spend at a set amount, block sanctioned addresses (search snippet). — [CDP Wallet Policies launch](https://www.coinbase.com/developer-platform/discover/launches/policy-engine)
- **AgentKit** README: wallet providers are CDP, Privy and viem; AgentKit "does not gate transfers behind human approval, enforce spend caps, or allowlist destinations"; the default `walletActionProvider` can move funds; it points to LangChain middleware and a "guardrails" example combining human approval for transfers with prompt-injection filtering. — [coinbase/agentkit](https://github.com/coinbase/agentkit)
- `coinbase/cdp-sdk`: client libraries (TS, Python, Go, Rust) "for managing EVM and Solana wallets while relying on CDP to secure private keys" (Wallet API v2). — [coinbase/cdp-sdk](https://github.com/coinbase/cdp-sdk)
- "Coinbase Agentic Wallets" reportedly launched 2026-02-11 on top of CDP Server Wallets v2 with session caps and per-transaction limits, TEE-secured keys, and EIP-7702 smart-account features; one vendor blog claims 25,000+ upgraded wallets and a "$450K Lobstar Wilde" incident — **unverified, single vendor source**. — [BlockEden (vendor blog)](https://blockeden.xyz/blog/2026/03/10/eip-7702-session-keys-ai-agent-defi-custody/); [Eco support article](https://eco.com/support/support/en/articles/14845485-coinbase-agentic-wallets)
- **Turnkey policy engine**: policies are JSON with `policyName`, `notes`, `effect` (`EFFECT_ALLOW`/`EFFECT_DENY`), `consensus` (who may approve, e.g. `approvers.any(user, user.id == '<id>')`) and `condition` (when it applies, e.g. `eth.tx.to == '<addr>'`); evaluation order: root quorum → explicit deny → any allow → implicit deny; "almost all actions are implicitly denied unless a policy allows them"; root quorum bypasses policies. — [tkhq/docs policy-engine.mdx](https://github.com/tkhq/docs/blob/main/snippets/shared/policy-engine.mdx)
- **Privy**: TEE key management; "supports policy enforcement like spending limits and transaction restrictions"; a competitor describes its controls as "fixed policy controls" (vendor comparison; primary docs blocked). — [Crossmint: agent wallets compared](https://crossmint.com/learn/agent-wallets-compared); [Turnkey vs Privy (vendor)](https://www.turnkey.com/vs/privy)
- **Crossmint**: default wallet is a smart-contract wallet "so policies like spending limits, allowlists, multi-sig approvals, and delegated signers are enforced onchain rather than at the application layer"; supports AWS KMS and Google Cloud KMS as signers (vendor pages). — [Crossmint agent wallets compared](https://crossmint.com/learn/agent-wallets-compared); [Crossmint Cloud KMS signer guide](https://docs.crossmint.com/wallets/guides/signers/cloud-kms); [Crossmint AWS KMS signer](https://docs.crossmint.com/stablecoin-orchestration/treasury-wallet/guides/signer-aws-kms)

### Takeaway

## Key Question 4 — Key management for the bureau signing service: cloud KMS secp256k1, Safe with KMS signers, threshold ECDSA providers, rotation and discovery (key registry, ERC-1271)

### Takeaway
AWS KMS and GCP KMS both support secp256k1 (`ECC_SECG_P256K1`) with `kms:Sign`/`kms:GetPublicKey`, and the integration pattern is well-trodden (DER → r,s,v with low-s normalisation and recovery-id derivation; address from the uncompressed 65-byte public key via viem's `publicKeyToAddress`). The robust rotation pattern is to make the *verifier-facing identity* a contract (Safe or a small ERC-1271 signer contract) so attestation verification keeps working while the KMS keys behind it rotate; Safe multisig with KMS-backed EOA owners is the standard intermediate step before true threshold ECDSA (Turnkey, Fireblocks, dfns, Cubist, Lit).

### Cited Findings
- AWS KMS key spec `ECC_SECG_P256K1` "is the secp256k1 elliptic curve, which is the same curve used by Ethereum"; required IAM actions are `kms:GetPublicKey` and `kms:Sign`; AWS returns the public key as PEM/DER, so it must be converted to the uncompressed 65-byte `0x04…` form before `publicKeyToAddress` (viem) — Crossmint's guides do exactly this for GCP KMS and AWS KMS (search snippets; pages blocked). — [Crossmint Cloud KMS signer](https://docs.crossmint.com/wallets/guides/signers/cloud-kms); [Crossmint AWS KMS signer](https://docs.crossmint.com/stablecoin-orchestration/treasury-wallet/guides/signer-aws-kms); [Nethereum Cloud KMS signing](https://docs.nethereum.com/docs/signing-and-key-management/guide-cloud-kms); [Mentaport: configuring AWS KMS for Web3](https://mentaport.substack.com/p/part-1-foundations-and-setup-configuring)
- Nethereum ships a ready-made AWS KMS external signer package; AWS also documents Nitro Enclaves for blockchain key management (search snippets). — [Nethereum.Signer.AWSKeyManagement](https://www.nuget.org/packages/Nethereum.Signer.AWSKeyManagement/); [AWS Nitro Enclaves for blockchain key management](https://aws.amazon.com/blogs/database/part-1-aws-nitro-enclaves-for-secure-blockchain-key-management)
- ERC-1271 contract signatures: `isValidSignature(bytes32,bytes)` must be `view`, returns `0x1626ba7e`; spec warns callers not to hard-code a gas limit; "each implementer is responsible for correctness". — [ERC-1271](https://github.com/ethereum/ERCs/blob/master/ERCS/erc-1271.md)
- OpenZeppelin 5.4+ provides `SignatureChecker` with ERC-7913 support (signer = `verifier || key`, enabling P256/RSA/WebAuthn and rotating keys without redeploying), `MultiSignerERC7913` / `MultiSignerERC7913Weighted` (threshold of ERC-7913 signers), ERC-7739 defensive rehashing for ERC-1271 signers, and `isValidERC1271SignatureNowCalldata` (5.6). — [openzeppelin-contracts releases](https://github.com/OpenZeppelin/openzeppelin-contracts/releases)
- Coinbase Spend Permissions verify approvals through `PublicERC6492Validator.isValidSignatureNowAllowSideEffects`, i.e., ERC-1271 + ERC-6492 for counterfactual accounts — a worked example of contract-signer verification in production. — [SpendPermissionManager.sol](https://github.com/coinbase/spend-permissions/blob/main/src/SpendPermissionManager.sol)

- Lit Protocol PKPs: "Lit Protocol PKPs" appear in agent-wallet roundups but the js-sdk repo URL I tried returned 404 and the docs host was blocked — no verified citation. — (none)
- Crossmint: smart-contract wallets with "delegated signers" and on-chain multisig approvals; supports AWS/GCP KMS as a signer type (vendor page). — [Crossmint agent wallets compared](https://crossmint.com/learn/agent-wallets-compared)

### Inferences
- **Signing path recommendation (consistent with the consumer's plan):** Phase 1 — single KMS key (AWS `ECC_SECG_P256K1`, GCP `EC_SIGN_SECP256K1_SHA256`) behind an IAM policy that only the bureau service role can `kms:Sign` with; wrap it as a viem `toAccount({ signMessage, signTypedData, signTransaction })` custom account; always normalise `s` to low-s and recover `v` by trying both parities against the known public key. Phase 2 — Safe (v1.4.1 canonical on Base) whose owners are two or three KMS-backed EOAs in separate accounts/regions; sign attestations with the Safe via ERC-1271 (`isValidSignature` over the EIP-712 digest), or use OZ `MultiSignerERC7913` as a leaner contract signer. Phase 3 — threshold ECDSA provider (Turnkey/Fireblocks/dfns/Cubist) or Lit PKP, still fronted by the same contract signer so verifiers never change.
- **Rotation/discovery:** Because attestations are verified against an *address*, make the canonical signer address a contract (Safe/ERC-1271 signer) and publish it in an on-chain registry contract the consumer already plans (UUPS, timelocked). Rotation then = Safe owner swap (no verifier change). If raw EOA signers must be used, the registry should store `(keyId, address, validFrom, validUntil)` so old attestations remain verifiable after rotation, and signed messages should embed `keyId` and chain-id in the EIP-712 domain.
- EIP-712 + nonces: OZ 5.7 tightened `EIP712` (name/version ≤31 bytes) and added ERC-3009-style parallel nonces (`ERC20TransferAuthorization`) — parallel/keyed nonces are preferable to sequential nonces for a signer that issues many attestations concurrently.

## Key Question 6 — Base L2 specifics: sequencer centralization, forced inclusion via L1, reorg behaviour and finality guidance for indexers

### Takeaway
Base is an OP-Stack rollup: a single sequencer orders L2 blocks, but any user can force a transaction by calling `OptimismPortal.depositTransaction` on L1; deposits are protocol-mandated inputs (derived from L1 `TransactionDeposited` events, first block of each epoch) and are normally included within ~30 minutes, or deterministically after the 12-hour sequencing window (`seq_window_size = 3600` L1 blocks on OP Mainnet; Base's own config file could not be fetched). For indexers: the `unsafe` head (sequencer pre-confirmations) can be reorged if it fails consolidation against L1-derived data; the `safe` head "may only be reorged out due to L1 reorgs"; the `finalized` head is derivable from finalized L1 (~2 beacon epochs ≈ 13 minutes).

### Cited Findings
- OP Stack forced transactions: users send transactions directly to the L1 `OptimismPortal`, bypassing the sequencer; the sequencing window is a rolling 12-hour delay; deposits are normally included within a 30-minute max time drift; if the sequencer is down 30 min–12 h, forced deposits are included once the sequencer resumes or the window expires (sequencer catch-up produces deposit-only blocks); beyond 12 h, nodes deterministically produce blocks containing only forced transactions. — [OP docs: forced-transaction.mdx](https://github.com/ethereum-optimism/docs/blob/main/pages/stack/transactions/forced-transaction.mdx)
- OP deposits spec: deposited transactions "must be included as part of the protocol" because they are derived from L1 blocks; user deposits come from `TransactionDeposited` events and appear only in the first block of an L2 epoch; an L2 block containing only the derivation-required deposits must be valid; deposits buy L2 gas on L1 via the guaranteed gas market (non-refundable, capped per L1 block). — [OP specs: deposits.md](https://github.com/ethereum-optimism/specs/blob/main/specs/protocol/deposits.md)
- OP derivation spec: unsafe head = not yet derived from L1 ("latest"); safe head = "everything up to and including this block can be fully derived from the currently canonical L1 chain"; finalized head = derivable from finalized L1; "The safe L2 head may only be reorged out due to L1 reorgs"; if unsafe blocks fail consolidation against derived L1 inputs, the derived attributes win and cause an L2 reorg on top of the current safe block; post-merge L1 reorg depth is bounded by ~2 beacon epochs (~13 min) absent >1/3 persistent disagreement. — [OP specs: derivation.md](https://github.com/ethereum-optimism/specs/blob/main/specs/protocol/derivation.md)

### Inferences
- Indexer policy: treat `unsafe` (sequencer-confirmed, ~2 s) as provisional UI state; treat `safe` as the point to act irreversibly off-chain (it can only reorg with L1, bounded ≈13 min); use `finalized` for anything that triggers money movement outside the chain (e.g., bureau releasing attestations/credit). Query by block tag (`safe`/`finalized`) rather than fixed confirmation counts, and design the indexer to handle a reorg of the unsafe segment back to the safe head.
- Censorship resistance for the agent/bureau: if the Base sequencer censors a revocation or pause, the owner can force it via `depositTransaction` within ≤12 h (usually ≤30 min). Revocation and pause paths should therefore be callable from an L1-originated deposit (msg.sender aliasing applies to contract senders — ensure the guardian/owner is an EOA or handle aliasing).
- Sequencer centralization: Base runs a single Coinbase-operated sequencer (OP-Stack model); the only trust-minimised escape hatch is the portal deposit path above plus L1 withdrawals via the fault-proof/`DisputeGameFactory` path (not verified in this session).
