## Q1. ERC-8004 "Trustless Agents": status, registries, addresses, chains, maintainers, planned revisions, Validation Registry on mainnet

### Takeaway
ERC-8004 is still a **Draft** ERC (created 2025-08-13, authors from MetaMask, EF, Google, Coinbase); the Identity and Reputation registries are deployed at vanity addresses `0x8004A169...` / `0x8004BAa1...` on 25 mainnets including Ethereum, Base and BSC, but the official contracts README publishes **no Validation Registry address on any chain** and says that section of the spec is still being revised with the TEE community. A mainnet Validation Registry address (`0x8004Cc84...`) circulates from a single third-party audit and could not be verified here.

**Identity Registry**
- Built on ERC-721 with the URIStorage extension so agents are "immediately browsable and transferable with NFTs-compliant apps"; `agentId` is the ERC-721 tokenId; `agentRegistry` is a colon-separated string `{namespace}:{chainId}:{identityRegistry}` (example `eip155:1:0x742...`); `agentURI` MUST resolve to a registration file and may be `ipfs://`, `https://` or a base64 `data:` URI — [erc-8004.md](https://raw.githubusercontent.com/ethereum/ERCs/master/ERCS/erc-8004.md); [ERC8004SPEC.md in contracts repo](https://raw.githubusercontent.com/erc-8004/erc-8004-contracts/main/ERC8004SPEC.md)
- Registration file fields: `type` (`"https://eips.ethereum.org/EIPS/eip-8004#registration-v1"`), `name`, `description`, `image`, `services` (example names: web, A2A, MCP, OASF, ENS, DID, email; the A2A example endpoint is `https://agent.example/.well-known/agent-card.json`), `x402Support`, `active`, `registrations` (array of `{agentId, agentRegistry}`), optional `supportedTrust` (example `["reputation", "crypto-economic", "tee-attestation"]`). "If `supportedTrust` is absent or empty, the ERC is used only for discovery, not for trust." — [ERC8004SPEC.md](https://raw.githubusercontent.com/erc-8004/erc-8004-contracts/main/ERC8004SPEC.md); [erc-8004.md](https://raw.githubusercontent.com/ethereum/ERCs/master/ERCS/erc-8004.md)
- Optional domain verification: an agent may publish `https://{endpoint-domain}/.well-known/agent-registration.json` to prove control of an endpoint domain — [erc-8004.md](https://raw.githubusercontent.com/ethereum/ERCs/master/ERCS/erc-8004.md)
- On-chain metadata via `getMetadata`/`setMetadata` (emits `MetadataSet`); the key `agentWallet` is reserved and set through `setAgentWallet()` with an EIP-712 or ERC-1271 signature; registration uses `register()` with optional `agentURI` and metadata; `setAgentURI()` emits `URIUpdated` — [erc-8004.md](https://raw.githubusercontent.com/ethereum/ERCs/master/ERCS/erc-8004.md)
- The Identity Registry contract is "an upgradeable ERC-721 (`ERC721URIStorage`)"; the repo labels all three contracts as upgradeable (`ValidationRegistryUpgradeable.sol` etc.) — [README](https://raw.githubusercontent.com/erc-8004/erc-8004-contracts/main/README.md)
- The spec file still "contains unresolved editor's notes and TODO comments" — [ERC8004SPEC.md](https://raw.githubusercontent.com/erc-8004/erc-8004-contracts/main/ERC8004SPEC.md)

**Reputation Registry**
- Function: `giveFeedback(uint256 agentId, int128 value, uint8 valueDecimals, string tag1, string tag2, string endpoint, string feedbackURI, bytes32 feedbackHash)`; `valueDecimals` 0–18; the submitter MUST NOT be the agent owner or an approved operator; other functions `revokeFeedback`, `appendResponse`, `getSummary`, `readFeedback`, `readAllFeedback`; `getSummary` requires a non-empty `clientAddresses` list "to mitigate Sybil and spam attacks"; example tags `starred`, `reachable`, `uptime`, `responseTime`; off-chain feedback files may include `proofOfPayment` (x402) — [erc-8004.md](https://raw.githubusercontent.com/ethereum/ERCs/master/ERCS/erc-8004.md); [ERC8004SPEC.md](https://raw.githubusercontent.com/erc-8004/erc-8004-contracts/main/ERC8004SPEC.md)
- The current spec text contains no `feedbackAuth` parameter, no `score`, no `fileuri`/`filehash` names (older drafts used those; current names are `value`, `feedbackURI`, `feedbackHash`) — [erc-8004.md](https://raw.githubusercontent.com/ethereum/ERCs/master/ERCS/erc-8004.md)

**Validation Registry**
- `validationRequest(validatorAddress, agentId, requestURI, requestHash)` MUST be called by the agent owner or operator; `validationResponse(requestHash, response, responseURI, responseHash, tag)` MUST be called by the named validator, `response` is 0–100 and may be called multiple times per request; "Incentives and slashing related to validation are managed by the specific validation protocol" / outside scope; the abstract names "stake-secured re-execution, zero-knowledge machine learning (zkML) proofs, or trusted execution environment (TEE) oracles" as example methods, not an enumeration — [erc-8004.md](https://raw.githubusercontent.com/ethereum/ERCs/master/ERCS/erc-8004.md)
- README warning (verbatim): "The Validation Registry portion of the ERC-8004 spec is still under active update and discussion with the TEE community." and "This section will be revised and expanded in a follow-up spec update later this year." — [README](https://raw.githubusercontent.com/erc-8004/erc-8004-contracts/main/README.md)

### Inferences
- For a credit bureau keyed on `agentId`, the globally unique key is the tuple `(agentRegistry = eip155:<chainId>:<registryAddress>, agentId)`, not `agentId` alone: the same vanity address `0x8004A169...` exists on 25 mainnets with independent tokenId sequences, so Base agentId 54848 and Ethereum agentId 54848 are different agents.
- Because the registries are upgradeable proxies with no published admin/multisig or audit information, the key's semantics (and even the ABI, per the `agentExists()` mismatch reported in ChaosChain#15) can change without an ERC version bump; the bureau should pin the ABI it indexes and watch `Upgraded` events.
- The Validation Registry should be treated as absent on mainnet for design purposes: even if the `0x8004Cc84...` deployment exists, it has no official documentation, had zero events in the one audit that looked, and the spec section is explicitly unstable.

## Q2. Empirical adoption of ERC-8004 and fact-check of the "3–15% valid / 85–97% empty shells" claim attributed to arXiv 2606.26028

### Takeaway
arXiv 2606.26028 ("Can Trustless Agents Be Trusted? An Empirical Study of the ERC-8004 Decentralized AI Agent Ecosystem") exists and its per-chain figures (3% Ethereum, 4% BSC, 15% Base of registrations with a valid registration file and live endpoint, data through 2026-05-13) support the "3–15%" range; the "85–97% are empty shells" phrasing is a paraphrase/inversion not found in the paper or any secondary source, and it conflates "no live endpoint" with "no registration file" (a separate measure shows 53%/9%/37% with no URI ever set on Ethereum/BSC/Base). Several independent studies (2606.12128, 2606.25876, 2604.22652, the yaojin0609 liveness census) converge on "registration-heavy, operationally shallow".

### Cited Findings

**The paper itself**
- arXiv:2606.26028, "Can Trustless Agents Be Trusted? An Empirical Study of the ERC-8004 Decentralized AI Agent Ecosystem", by Xihan Xiong and five coauthors; first submitted June 24 2026; v3 dated October 18 2026 (via search; arxiv.org not fetchable) — [arXiv abs](https://arxiv.org/abs/2606.26028); [HTML v2](https://arxiv.org/html/2606.26028v2); [PDF](https://arxiv.org/pdf/2606.26028)
- Scope: crawls on-chain identity and reputation events across Ethereum, BNB Smart Chain and Base from deployment through May 13 2026; 173,441 agents in sample; "the first empirical study of ERC-8004 across three chains" (via search) — [arXiv abs](https://arxiv.org/abs/2606.26028)
- Identity finding: "only about 3%, 4%, and 15% of registrations on Ethereum, BSC, and Base, respectively, have a valid registration file with a live service endpoint (most registrations are placeholders rather than active agents)" (via search) — [arXiv abs](https://arxiv.org/abs/2606.26028)
- Reputation finding: coordinated Sybil reviewers at 73.5% (Ethereum), 59.2% (BSC), 90.6% (Base); after removing Sybil-flagged feedback, 15.8%, 77.9% and 86.8% of rated agents respectively are left with no valid feedback (via search; the Sybil figures are also quoted verbatim in contracts issue #99) — [arXiv abs](https://arxiv.org/abs/2606.26028); [erc-8004-contracts#99](https://github.com/erc-8004/erc-8004-contracts/issues/99)
- The paper also finds reputations are chain-specific and do not transfer across deployments (via search) — [Concordium summary](https://www.concordium.com/article/erc-8004-explained-what-it-solves-and-the-gap-it-leaves)
- An AI-generated third-party review (Pith) calls the Sybil numbers "the softest part of the paper" while saying the design critique holds without them (via search; treat as low-weight) — [Pith](https://pith.science/paper/2606.26028)
- No source containing the phrase "empty shells" was found; a search for the exact phrase with "ERC-8004" returned only generic explainers — [datawallet explainer](https://www.datawallet.com/crypto/erc-8004-explained); [eco.com explainer](https://eco.com/support/en/articles/13221214-what-is-erc-8004-the-ethereum-standard-enabling-trustless-ai-agents)
- Secondary explainer (datawallet) citing "two academic audits from June and July": 3% of Ethereum agents vs 15% on Base have a valid registration file plus at least one service endpoint; 53% of Ethereum agents never had a URI set, vs 37% on Base and 9% on BNB Smart Chain; "free minting has filled registries with empty or non-compliant entries" (via search) — [datawallet](https://www.datawallet.com/crypto/erc-8004-explained)

**Other measurement studies**
- arXiv:2606.12128 "From Agent Identity to Agent Economy: Measuring the Operational Readiness of ERC-8004 AI Agents": of 10,000 registered agents (Ethereum dataset), only 67 expose service records, 628 receive reputation feedback, and 19 combine all tracked signals; concludes early adoption is "registration-heavy but operationally shallow" (via search) — [arXiv html](https://arxiv.org/html/2606.12128v1); [HF paper page](https://huggingface.co/papers/2606.12128)

- arXiv:2604.22652 "A dataset of early blockchain-registered AI agents on Ethereum" (Yulin Liu, Quantum Economics AI Lab, Zurich): 10,000 agents within a block range; on-chain identity records, minting transactions, **transfer events**, reputation summaries, feedback records, plus resolved off-chain metadata; notes the validation component "remains immature in current deployments and does not yet provide comparable observable data" (via search) — [arXiv pdf](https://arxiv.org/pdf/2604.22652); [HF](https://huggingface.co/papers/2604.22652)
- Liveness census (yaojin0609/erc-8004-liveness, snapshot 2026-08-10, 12 chains, re-run planned 2026-11-10): 392,258 identities; 21.3% declare routable service endpoints; 47.6% of probed identities completed an A2A/MCP protocol-level handshake in two rounds 48h apart (38.6% reweighted by host stratum); BSC 262,999 identities (~67%); method: `ownerOf`/`tokenURI`/`getAgentWallet` via Multicall3 plus event logs, A2A checked by fetching/parsing the agent card, MCP by `initialize` + `tools/list`; no per-chain Base figure — [github.com/yaojin0609/erc-8004-liveness](https://github.com/yaojin0609/erc-8004-liveness)

### Inferences
- The design-document claim should be rewritten as: "Per arXiv 2606.26028 (data to 2026-05-13), only 3% (Ethereum), 4% (BSC) and 15% (Base) of registered agents had a valid registration file *and* a live service endpoint; the remainder are placeholders, of which a large subset (53%/9%/37%) never set a URI at all." The complementary "85–97%" is arithmetically implied but is not the paper's wording and should not be attributed in quotes.
- Base is simultaneously the chain with the highest valid-registration rate (15%), the highest Sybil-reviewer rate (90.6%) and ~79% of all feedback volume, which means Base feedback volume is the least trustworthy raw input for a bureau while Base identities are the most likely to be real.
- Counts differ by 3–5x across sources (173k three-chain / 387k 26-chain / 392k 12-chain / 519k 30-chain) because of snapshot date and chain set; for a Base bureau, the Base-only figures (33,939 indexed in awesome list, undated; 67,889 on 8004scan at Sep 18 2026; agentIds up to ~54,848 observed in June 2026) are the relevant denominators.

### Gaps
- The paper's full text and exact abstract could not be read (arxiv.org blocked); the precise definition of "valid registration file with a live service endpoint" (e.g., whether a reachable but non-conformant A2A card counts) is unverified.
- The claim of "two academic audits from June and July" (datawallet) could not be mapped to specific papers beyond 2606.26028 and 2606.12128.
- No October 2026 registration count was found; the latest dated aggregate is Sep 18 2026.
- No per-chain breakdown for Base in the liveness census.

## Q3. Registration file vs A2A Agent Card; A2A extensions; ENSIP-25

### Takeaway
ERC-8004's registration file is a separate JSON (type `...eip-8004#registration-v1`) that *points to* an A2A Agent Card at `/.well-known/agent-card.json` (A2A 1.0 canonical path; `agent.json` is the pre-1.0 legacy path); A2A 1.0 provides JWS-signed cards and a URI-keyed extensions mechanism but does not itself reference DIDs or ERC-8004. ENSIP-25 (Draft, 2025-10-02) binds an ENS name to an ERC-8004 `(registry, agentId)` through a text record `agent-registration[<ERC-7930 registry>][<agentId>]`, verified in the registry-to-ENS direction only.

### Cited Findings

**ERC-8004 registration file ↔ A2A**
- The ERC-8004 registration file's `services` array example names A2A with `endpoint: https://agent.example/.well-known/agent-card.json`, alongside MCP, OASF, ENS, DID and email entries; the Motivation section says A2A "handles agent authentication, skills advertisement via AgentCards" — [ERC8004SPEC.md](https://raw.githubusercontent.com/erc-8004/erc-8004-contracts/main/ERC8004SPEC.md)
- awesome-erc8004 states ERC-8004 "extends" the A2A protocol and requires agent cards at `/.well-known/agent-card.json`; it describes no dedicated A2A extension URI for ERC-8004 — [awesome-erc8004](https://github.com/sudeepb02/awesome-erc8004)

**A2A Agent Card (spec)**
- Latest released A2A version: 1.0.0 (previous 0.3.0, 0.2.6, 0.1.0); protocol version identified as `Major.Minor` — [a2aproject/A2A specification.md](https://raw.githubusercontent.com/a2aproject/A2A/main/docs/specification.md)
- Discovery path: §8.2 "https://{server_domain}/.well-known/agent-card.json"; §14.3 (IANA) registers the well-known suffix `agent-card.json`, which "MUST return an AgentCard object" — [specification.md](https://raw.githubusercontent.com/a2aproject/A2A/main/docs/specification.md)
- The 1.0 spec text contains no mention of `agent.json`, deprecation notes, DIDs, blockchain, or ERC-8004 — [specification.md](https://raw.githubusercontent.com/a2aproject/A2A/main/docs/specification.md)
- Card fields: name, description, version, skills, supportedInterfaces (url, protocolBinding, protocolVersion, tenant), capabilities (streaming, pushNotifications, extensions, extendedAgentCard), defaultInput/OutputModes, securitySchemes/security, provider (organization, url), signatures — [specification.md](https://raw.githubusercontent.com/a2aproject/A2A/main/docs/specification.md)
- Extensions: declared in `capabilities.extensions` as AgentExtension objects with `uri`, `description`, `required`; clients opt in via the `A2A-Extensions` header (comma-separated URIs); if a client requests an unsupported extension version the agent SHOULD ignore it unless `required`, in which case it MUST error; no automatic fallback — [specification.md](https://raw.githubusercontent.com/a2aproject/A2A/main/docs/specification.md)
- Signed cards: cards MAY be signed with JWS (RFC 7515) over RFC 8785-canonicalized JSON; each AgentCardSignature has `protected` (base64url header with `alg`, `kid`, SHOULD `typ: JOSE`, MAY `jku`), `signature`, optional `header`; `signatures` excluded from signed content; clients SHOULD verify at least one signature; example uses ES256 with `jku` JWKS URL — [specification.md](https://raw.githubusercontent.com/a2aproject/A2A/main/docs/specification.md)
- 1.0 breaking changes: removed `kind` discriminator; moved `supportsExtendedAgentCard` to `capabilities.extendedAgentCard` — [specification.md](https://raw.githubusercontent.com/a2aproject/A2A/main/docs/specification.md)
- Secondary sources: A2A 1.0 released under Linux Foundation governance on 12 March 2026, 1.0.1 on 28 May 2026; `/.well-known/agent.json` is the legacy pre-1.0 path still checked by many deployed clients; advice diverges between a 308 redirect, dual publishing, or no redirect (via search; unverified against official release notes) — [agentcard.net](https://www.agentcard.net/blog/a2a-v1-0-agent-card-changes); [adcp issue #7875](https://github.com/adcontextprotocol/adcp/issues/7875)

**ENSIP-25**
- Title "ENSIP-25: AI Agent Registry ENS Name Verification"; Status Draft; Created 2025-10-02; contributors premm.eth, raffy.eth, workemon.eth, ses.eth; abstract: "a standard way to use ENS text records to verify that an ENS name is linked to an AI agent identity in a specific on-chain registry" — [ensdomains/ensips 25.md](https://raw.githubusercontent.com/ensdomains/ensips/master/ensips/25.md)
- Text-record key `agent-registration[<registry>][<agentId>]`, where `<registry>` is the registry contract as an ERC-7930 interoperable address (0x-prefixed) and `<agentId>` is the registry-defined id (must not contain `[` or `]`); value MUST be non-empty, implementations SHOULD use `"1"`; a non-empty value is an attestation by the name owner — [25.md](https://raw.githubusercontent.com/ensdomains/ensips/master/ensips/25.md)
- Verification flow (registry→ENS): read claimed ENS name, agentId and registry from the registry entry; build the key; resolve on the claimed name; non-empty = verified. Example: ERC-8004 on Ethereum mainnet `0x8004A169FB4a3325136EB29fA0ceB6D2e539a432` → ERC-7930 `0x000100000101148004a169fb4a3325136eb29fa0ceb6d2e539a432`; key for agent 167: `agent-registration[0x000100000101148004a169fb4a3325136eb29fa0ceb6d2e539a432][167]` — [25.md](https://raw.githubusercontent.com/ensdomains/ensips/master/ensips/25.md)
- Security: if a name changes owners, records may be stale; clients should account for ownership changes and may apply freshness/revocation checks; no resolver upgrade needed, single lookup — [25.md](https://raw.githubusercontent.com/ensdomains/ensips/master/ensips/25.md)
- Because the registry address is ERC-7930 (chain-qualified), an agent registered on Base can be checked against an ENS name on L1 (via search, secondary) — [nncoe.vercel.app](https://nncoe.vercel.app/); [ENS blog](https://ens.domains/blog/post/ensip-25)
- A Rust crate `ensip25` implements the key construction — [docs.rs/ensip25](https://docs.rs/ensip25/latest/ensip25/)
- ENSIP-26 "ENS Native AI Identity" (agent metadata/endpoints on ENS, complementary to ENSIP-25) is under discussion on the ENS DAO forum (via search) — [discuss.ens.domains](https://discuss.ens.domains/t/ensip-26-ens-native-ai-identity/21968)

### Inferences
- There is no standardized A2A extension URI that carries an ERC-8004 agentId; the linkage today is one-directional (registration file → agent card) plus optional domain proof (`/.well-known/agent-registration.json`). A bureau that wants card→registry binding must either parse that well-known file or rely on ENSIP-25 for a name-level attestation.
- ENSIP-25 gives the bureau a cheap second signal of operator intent (name owner attested to the `(registry, agentId)` pair) but, like the registry, it is not re-attested on NFT transfer, so it should be re-checked after any `Transfer` event.

- The first 100k characters of the A2A spec did not include the formal AgentExtension `params` field; whether `params` exists in 1.0 is unverified.
- ENSIP-25 adoption counts (how many ENS names carry `agent-registration[...]` records) were not found.

## Q4. Non-blockchain agent identity: DIDs, HCS-14 UAID, Web Bot Auth, WIMSE/SPIFFE, Entra Agent ID, Okta/Auth0, Google, NANDA, ANS, OpenID Foundation, W3C CG

### Takeaway
Off-chain agent identity is fragmenting along what it binds: keys/accounts (did:key, did:pkh, Web Bot Auth), domains (did:web, NANDA `urn:air:`, ANS, Web Bot Auth directory), enterprise tenants/software (Entra Agent ID, Okta/Auth0 CIMD + ID-JAG, Google SPIFFE Agent Identity, WIMSE AIMS), or a hash of metadata (HCS-14 UAID). Only HCS-14 (which already publishes profiles for ERC-8004 agents) and ENS/did:pkh (which naturally map to the token-owner address) have an evident path to carrying an ERC-8004 reference; the enterprise systems have no documented external-identifier field.

## Q5. Ownership-transfer semantics of the ERC-8004 agentId NFT and "reputation purchase"

### Takeaway
The agentId is a freely transferable ERC-721 token; the spec only clears the `agentWallet` metadata on transfer, while all Reputation and Validation records stay attached to the agentId, so a sold token carries its history to the buyer. The "reputation laundering" risk has been raised in community analyses and blog posts, but no official transfer restriction, soulbound option, or reputation-reset mechanism exists in the spec.

### Cited Findings
- ERC-8004 Identity Registry is ERC-721 so agents are "transferable with NFTs-compliant apps"; the token owner "can transfer ownership or delegate management" to operators; "When the agent is transferred, `agentWallet` is automatically cleared" and "must be re-verified by the new owner"; the spec does not say whether operators are cleared on transfer — [ERC8004SPEC.md](https://raw.githubusercontent.com/erc-8004/erc-8004-contracts/main/ERC8004SPEC.md); [erc-8004.md](https://raw.githubusercontent.com/ethereum/ERCs/master/ERCS/erc-8004.md)
- Feedback and validation are keyed to `agentId` (`giveFeedback(uint256 agentId, ...)`, `validationRequest(..., agentId, ...)`); no function resets them on transfer — [erc-8004.md](https://raw.githubusercontent.com/ethereum/ERCs/master/ERCS/erc-8004.md)
- Analysis: "since the agent's reputation and validation records are tied to the agentId (token ID), those remain with the token on transfer. This is good (reputation is part of the agent asset being transferred) but also raises considerations" about a new owner who may be better or worse (via search) — [Medium: ERC-8004 technical, economic and policy analysis](https://medium.com/@gwrx2005/erc-8004-and-the-ethereum-ai-agent-economy-technical-economic-and-policy-analysis-3134290b24d1)
- "The Reputation Laundering Problem in Agent Commerce" (Revettr): an agent can build a strong record and sell the NFT, leaving the buyer with unearned history; the registry does not track whether the wallet or operator behind the agent changed; proposes a scoring layer that watches `Transfer` events and registration-file changes (via search) — [Revettr](https://revettr.com/blog/the-reputation-laundering-problem)
- The opposite risk, "whitewashing" (abandon a badly rated identity and mint a new one, since minting is free), is noted by the same commentary cluster and by the datawallet explainer on free minting (via search) — [Concordium](https://www.concordium.com/article/erc-8004-explained-what-it-solves-and-the-gap-it-leaves); [datawallet](https://www.datawallet.com/crypto/erc-8004-explained)
- Mitigation cited: transfers are public — "you would just see on a block explorer that the nft had been recently transferred" (via search) — [datawallet](https://www.datawallet.com/crypto/erc-8004-explained)
- Allium argues a bad actor "cannot quietly wipe negative feedback and reappear clean" (about erasure, not purchase) (via search) — [Allium](https://www.allium.so/blog/onchain-ai-identity-what-erc-8004-unlocks-for-agent-infrastructure/)
- The Ethereum dataset paper (2604.22652) includes transfer events for 10,000 Ethereum agents, so transfer frequency is measurable from that dataset (via search) — [arXiv 2604.22652](https://arxiv.org/pdf/2604.22652)
- ERC-8122 (competing minimal registry) is also transferable — [erc-8122.md](https://raw.githubusercontent.com/ethereum/ERCs/master/ERCS/erc-8122.md)
- A relevant X/Twitter thread by "YQ" (Nov 2025) was surfaced by search but its content could not be read — [x.com/yq_acc](https://x.com/yq_acc/status/1985302546349425147)

### Inferences
- For a credit bureau, the ERC-721 `Transfer(from, to, tokenId)` event is a mandatory input: a bureau file keyed on agentId must at minimum version its record at each transfer (a "new account holder" event), re-check `agentWallet`, ENSIP-25 records and the registration file, and probably discount pre-transfer history unless the operator/wallet continuity can be shown.
- Because `getSummary` requires caller-supplied `clientAddresses`, the registry design already pushes Sybil-filtering responsibility to consumers like a bureau; the Sybil rates measured (59–91%) mean raw on-chain feedback cannot be used without such filtering.

### Gaps
- No quantitative study of how often ERC-8004 agentIds are transferred, or of secondary-market sales of agentIds, was found.
- No official maintainer statement (spec text, Magicians thread) on soulbound/non-transferable variants or on resetting reputation at transfer was found; the Ethereum Magicians thread could not be fetched.
- Whether approved operators persist across transfer in the deployed (upgradeable) contract bytecode is unverified; the spec is silent and the contracts were not inspected.
