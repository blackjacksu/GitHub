## Key Question 1: Ethereum Attestation Service (EAS) — version, maintainers, deployments, off-chain format, revocation, resolvers, SDK, tooling, gas, production users

### Takeaway
EAS is an MIT-licensed, two-contract protocol (SchemaRegistry + EAS) whose contract version is 1.4.0 (EIP-712 domain "EAS"/"1.4.0") in source, but the Base and Optimism predeploys are v1.0.1 at 0x4200...0021 (EAS) and 0x4200...0020 (SchemaRegistry); Ethereum mainnet and Arbitrum One run older v0.26 deployments at non-predeploy addresses. Off-chain attestations are EIP-712-signed objects; they are "revoked" by the signer calling `revokeOffchain(bytes32 uid)` on-chain, which records a timestamp keyed by `(revoker, uid)`, so verifiers must query `getRevokeOffchain(bureauAddress, uid)`.

**On-chain attestation model, refUID, resolvers**
- `AttestationRequestData` fields: `recipient`, `expirationTime` ("Unix timestamp"), `revocable`, `refUID` ("The UID of the related attestation"), `data`, `value` ("An explicit ETH amount to send to the resolver"). Events: `Attested(recipient, attester, uid, schemaUID)`, `Revoked(...)`, `Timestamped(data, timestamp)`, `RevokedOffchain(revoker, data, timestamp)` — [IEAS.sol](https://github.com/ethereum-attestation-service/eas-contracts/blob/master/contracts/IEAS.sol)
- In `_attest`, a non-empty `refUID` must already exist: `isAttestationValid(request.refUID)` else revert `NotFound()` ("Ensure that we aren't trying to attest to a non-existing referenced UID") — [EAS.sol](https://github.com/ethereum-attestation-service/eas-contracts/blob/master/contracts/EAS.sol)
- Resolver call path: `_resolveAttestation` reverts `NotPayable` if value is sent to a non-payable resolver, checks `resolver.isPayable()`, calls `resolver.attest{value}(attestation)` / `resolver.revoke{value}(attestation)`, and a `false` return reverts with `InvalidAttestation` / `InvalidRevocation`; batch path uses `multiAttest` / `multiRevoke`; unused ETH is refunded — [EAS.sol](https://github.com/ethereum-attestation-service/eas-contracts/blob/master/contracts/EAS.sol)
- `SchemaResolver` is `abstract contract SchemaResolver is ISchemaResolver, Semver`; child contracts implement `onAttest(Attestation calldata attestation, uint256 value) internal virtual returns (bool)` and `onRevoke(...)`; `isPayable()` returns false by default; all external entry points use `onlyEAS` (`msg.sender != address(_eas)` reverts `AccessDenied`) — [SchemaResolver.sol](https://github.com/ethereum-attestation-service/eas-contracts/blob/master/contracts/resolver/SchemaResolver.sol)
- The canonical attester-restriction pattern the consumer plans to use already exists as an example: `AttesterResolver` has `constructor(IEAS eas, address targetAttester)`, `onAttest` returns `attestation.attester == _targetAttester`, and `onRevoke` returns `true` — [AttesterResolver.sol](https://github.com/ethereum-attestation-service/eas-contracts/blob/master/contracts/resolver/examples/AttesterResolver.sol)
- EAS docs: a resolver is "an external smart contract that acts as a hook for a Schema"; examples listed: Attester Resolver ("only a particular entity is allowed to attest"), Paying, Token, Expiration time, Recipient, Revocation ("control over revocations"), Value resolvers; EAS "does not verify, endorse, or audit" resolvers — [eas-docs resolver-contracts.md](https://github.com/ethereum-attestation-service/eas-docs-site/blob/main/docs/core--concepts/resolver-contracts.md)
- Revocation docs: revocability is set at the schema level; revoking sets the attestation's `revoked` field to true; the record is not removed; EAS does not do "replacement" (old record stays; a new attestation "may reference the revoked attestation's UID to keep a clear history"); revocation "can be done both onchain and offchain" — [eas-docs revocation.md](https://github.com/ethereum-attestation-service/eas-docs-site/blob/main/docs/core--concepts/revocation.md)

**Off-chain attestation format, signing, timestamping, revocation**
- SDK: `const offchain = await eas.getOffchain(); offchain.signOffchainAttestation({recipient, expirationTime, time, revocable, schema, refUID, data}, signer)` returns "UID, signature, and attestation data"; "Starting from version `1`, we have added a `version` field to its typed data"; examples instantiate `new Offchain(EAS_CONFIG, OffchainAttestationVersion.Version2)`; `EAS_CONFIG` = `{address, version, chainId}` with the EIP-712 domain name `'EAS Attestation'` and example version `'0.26'`; legacy `getOffchainUID` requires `{version: 0}`; verification via `offchain.verifyOffchainAttestationSignature(signerAddress, sig)` — [eas-sdk README](https://github.com/ethereum-attestation-service/eas-sdk)
- SDK on-chain hooks for off-chain data: `eas.timestamp(data)`, `eas.multiTimestamp([...])`, `eas.revokeOffchain(data)`, `eas.multiRevokeOffchain([...])`; delegated flows `signDelegatedAttestation` / `attestByDelegation({signature, attester, deadline})` and `signDelegatedRevocation` / `revokeByDelegation` — [eas-sdk README](https://github.com/ethereum-attestation-service/eas-sdk)
- Contract semantics: `revokeOffchain(bytes32 data) external returns (uint64)` records a revocation "for `msg.sender`", stored in `_revocationsOffchain[revoker][data]`; `getRevokeOffchain(address revoker, bytes32 data)` reads it; `timestamp(bytes32 data)` stores the block time in `_timestamps[data]`; `multiRevokeOffchain` / `multiTimestamp` share one time across items — [EAS.sol](https://github.com/ethereum-attestation-service/eas-contracts/blob/master/contracts/EAS.sol)
- NatSpec in IEAS.sol for `revokeOffchain`: "Revokes the specified bytes32 data" / returns "The timestamp the data was revoked with" (the `@param` text says "to timestamp", apparently copy-pasted) — [IEAS.sol](https://github.com/ethereum-attestation-service/eas-contracts/blob/master/contracts/IEAS.sol)
- EAS docs: off-chain attestations are "tied to the blockchain through cryptographic signatures but are not stored on it"; the UID "can be timestamped onchain, giving the attestation verifiable proof of existence"; storage options are centralized servers, IPFS, or "URL hashes in browsers"; "Revocations for offchain attestations require separate management, whereas onchain revocations are stored onchain"; off-chain attestations have "no gas fees" — [eas-docs onchain-vs-offchain.md](https://github.com/ethereum-attestation-service/eas-docs-site/blob/main/docs/core--concepts/onchain-vs-offchain.md)
- EAS docs privacy page: easscan.org off-chain attestations live in the URL fragment so "the easscan.org server doesn't even know it exists" — [eas-docs privacy.md](https://github.com/ethereum-attestation-service/eas-docs-site/blob/main/docs/core--concepts/privacy.md)

### Inferences
- For the consumer's design (off-chain by default, on-chain on band change, resolver enforcing attester == bureau key): the resolver only executes inside `_attest`/`_revoke` on-chain; off-chain attestations never touch the resolver, so "attester == bureau" for off-chain claims must be enforced by verifiers checking the EIP-712 signer against the bureau's published key (and against the on-chain `getRevokeOffchain(bureau, uid)` map). `revokeOffchain` is also not resolver-gated and is keyed by `msg.sender`, so only revocations recorded under the bureau's own address are meaningful.
- Because off-chain revocation is a per-revoker timestamp map, there is no "revoke by anyone" and no on-chain reason field; a bureau wanting dispute outcomes or reason codes attached to a revocation should issue a new attestation with `refUID` pointing at the revoked UID (the pattern the EAS revocation docs describe).
- The EIP-712 domain `version` must match the deployed contract's version string (the SDK config takes `{address, version, chainId}`); on Base the predeploy is listed as v1.0.1, so off-chain attestations for Base should be signed against that domain, not "1.4.0". This is inferred from the README config structure plus the deployment table; confirm with `eas.getVersion()` at deploy time.
- If upgradability of the Base predeploy matters: the OP specs mark EAS/SchemaRegistry as "proxied", meaning the implementation can move with hardforks; the deployed version string (1.0.1) lags source (1.4.0).

## Key Question 2: Alternatives (Verax, Sign Protocol, Ceramic/ComposeDB, Disco, Veramo, W3C VC 2.0, SD-JWT VC, OpenID4VC) and EAS interoperability; Coinbase Verifications

### Takeaway
Verax (Consensys/Linea) and Sign Protocol (EthSign) are the two on-chain registries closest to EAS, both with EVM deployments including Base; Verax ships an explicit EAS-compatibility `AttestationReader`, Sign has a parallel `attestOffchain`/`revokeOffchain` model. W3C VC 2.0 / SD-JWT VC / OpenID4VC are the off-chain credential stack (now largely final), but EAS's own ZK playbook calls W3C VCs "not recommended" for smart-contract use because they need bridges; no native EAS-to-VC interop layer was found.

## Key Question 3: Privacy — selective disclosure and ZK over attestations; hashed operator identity and GDPR erasure

### Takeaway
EAS's official guidance is Merkle-root "private data attestations" for selective disclosure, off-chain attestations for confidentiality, and zkVM proofs (SP1/RISC Zero via templates like zkAttestify) for ZK claims over EAS data; the EDPB's finalised Guidelines 02/2025 treat hashes of personal data as still personal data, so the "orphaned hash" defence is contested rather than settled.

### Cited Findings
- EAS privacy guidance: attest to a Merkle tree and publish only the root; holders "can selectively disclose or verify specific items against that root" (transcript example); "once data is onchain, it's permanent"; never attest personal data directly on-chain; use hashes or privacy-preserving methods; ZKPs can be generated from attestation data and shared selectively — [eas-docs privacy.md](https://github.com/ethereum-attestation-service/eas-docs-site/blob/main/docs/core--concepts/privacy.md)
- EAS ZK playbook: "Provable claims, made privately"; quickstart proves "age > 18" using SP1; use cases include "autonomous agents acting on verified claims"; open research question: "What's the best way to generate zero-knowledge proofs from attestations?" — [eas-docs zk overview.md](https://github.com/ethereum-attestation-service/eas-docs-site/blob/main/docs/zk--playbook/overview.md)
- Recommended tooling: SP1 CLI + Verifier WASM template "Proves off-chain attestations, verifiable via WASM or Solidity"; zkAttestify "Converts any EAS off-chain attestation into a proof using SP1 or Risc Zero"; Icebreaker is a zkApp using Circom with EAS; zkVMs SP1, RISC Zero, Jolt, Boojum/Airbender; DSLs Circom 2/SnarkJS, Noir, Halo2/Arkworks — [eas-docs recommended-tooling.md](https://github.com/ethereum-attestation-service/eas-docs-site/blob/main/docs/zk--playbook/recommended-tooling.md)
- Semaphore: "a generic privacy layer" letting users prove group membership and send signals without revealing identity, off-chain or on EVM chains; circom/zk-SNARK based; linked to PSE (semaphore.pse.dev); 1,903 commits, 1.1k stars — [semaphore-protocol/semaphore](https://github.com/semaphore-protocol/semaphore)
- zk-X509 paper (arXiv 2603.25190) characterises Semaphore as anonymous signalling within a predefined group (no certificate-based identity) and zkPassport as on-device proofs over NFC passports/eIDs with selective disclosure of age/nationality/name — [arXiv 2603.25190](https://arxiv.org/pdf/2603.25190)
- Safe Research on ZK Passport: "full mode" proves issuer-signature validity and MRZ hash integrity on-device; "light mode" delegates signature checking to a trusted verifier; concerns: device limits, replay, personhood vs full identity — [Safe Research](https://safefoundation.org/blog/safe-research-zk-passport-where-are-we-now)
- Sismo: `sismo-core/sismo-hub` still describes ZK Badges and Sismo Connect; the repo page showed no archive banner or shutdown notice — [sismo-hub](https://github.com/sismo-core/sismo-hub)
- EDPB Guidelines 02/2025 on blockchain: law-firm summary says the EDPB "has published its final Guidelines 02/2025" with "very few changes" from the April 2025 draft — [Slaughter and May](https://thelens.slaughterandmay.com/post/102ndb2/edpb-finalises-guidelines-on-gdpr-and-blockchain); consultation responses quote the draft: "hashes of personal data will still be considered personal data, as will any other identifiers that still might exist" — [INATBA response (EDPB site)](https://www.edpb.europa.eu/sites/default/files/webform/public_consultation_reply/inatba-response_edpb-guidelines-2025-06-09.pdf); draft paragraph 63 flagged as suggesting erasure "may require deleting the whole blockchain" — [consultation reply](https://www.edpb.europa.eu/sites/default/files/webform/public_consultation_reply/comment-on-edpb-guidelines-02_2025-dennis-pasveer.pdf); summary: EDPB favours keeping personal data off-chain with only hashes/proofs on-chain — [ppc.land](https://ppc.land/edpb-forces-blockchain-firms-to-avoid-storing-personal-data-on-chain/)
- The "orphaned hash" framing (controller deletes off-chain data; on-chain hash "leaves a number with no correspondence") appears in a Grant Thornton brochure, not in EDPB text — [Grant Thornton GDPR & Blockchain](https://www.grantthornton.es/globalassets/1.-member-firms/spain/folletos/gdpr--blockchain.pdf)

### Inferences
- For a bureau publishing operator-linked claims: a salted/keyed hash of operator identity on-chain plus off-chain key material is the EDPB-tolerated pattern, but the guidelines' stance that hashes remain personal data means the defensibility of an orphaned hash depends on demonstrating that re-identification is no longer "reasonably likely" after off-chain deletion (controller-side destruction of salt/pepper strengthens this). Treat this as an unsettled argument, not a safe harbour.
- A ZK design that fits the consumer's schemas: issue off-chain EAS attestations (private), publish a Merkle root or band-change attestation on-chain, and let counterparties verify SP1/RISC Zero proofs over the off-chain attestation (zkAttestify pattern) — this matches EAS's own recommended stack and avoids putting KYA details on Base.

- No source found describing a production "EAS + ZK verifier as resolver" deployment; the EAS ZK playbook describes patterns and templates, not deployed systems.
- Sismo's operational status (widely reported wind-down) and Semaphore's current major version (v4) could not be verified in accessible sources.

## Key Question 4: Runtime and software attestation for agents (TEE stacks, binding quotes to agentId, supply-chain provenance, KYA tier 3 requirements)

### Takeaway
Every production "verifiable agent" stack found (Phala dstack/Phala Cloud, Oasis ROFL, Marlin Oyster, EigenCloud EigenCompute, NEAR AI, Flashbots BuilderNet/Flashtestations) is TEE-based (Intel TDX dominant, AWS Nitro for Marlin, NVIDIA CC GPUs for inference), and the common binding pattern is: derive the agent's signing key inside the TEE, put the derived address (or a hash of key + nonce) in the quote's `report_data`, verify the quote (Automata DCAP on-chain at ~4-5M gas, or ZK-wrapped at ~0.5M gas), and register the attested address/measurements against the agent identity (e.g., ERC-8004 agentId). No stack found attests the *model weights* or *LLM behaviour* beyond measuring the container/compose hash and (for GPU inference) the GPU firmware/driver state.

### Inferences
- Binding a TEE quote to an ERC-8004 agentId, as actually implemented today: (1) derive the agent key inside the CVM from the KMS (dstack `get_key(path, purpose)`), (2) put the derived address in `report_data` (Phala template) or `reportData[0:20]` + hash of extended data in `reportData[20:52]` (Flashtestations), (3) verify the quote on-chain (Automata DCAP ~4-5M gas, or ~0.5M with a ZK wrapper) and store the attested address + measurements, (4) set that address as the ERC-8004 `agentWallet` / mint the agentId from it, and optionally (5) record it through `validationResponse(..., tag="tee-attestation")` from a TEE-oracle validator. The agentId itself is not inside the quote in the Phala template; the link is address-based.
- "Software attestation (code hash or TEE quote)" at a KYA tier 3 realistically requires, at minimum: a reproducible build recipe and a published expected measurement set (for dstack: MRTD/RTMR0-2 + compose hash; for Nitro: PCR0/1/2 (+PCR16)), a fresh quote whose `report_data` binds the agent's on-chain key and a verifier nonce, DCAP/Nitro certificate-chain verification against current collateral (TCB status, advisories), and a policy allowlist of approved measurements (Flashtestations' WorkloadId / dstack's DstackApp compose-hash list) with a revocation path when collateral or code is deprecated. A code-hash-only tier (signed SLSA/in-toto provenance over a container digest, no TEE) proves what was built, not what is running; it is cheaper but should be scored lower.
- What TEE attestation does not give the bureau: assurance about model weights served by a third-party API (only the agent container is measured unless inference is also inside a CVM+GPU TEE, as in NEAR AI/EigenAI), or about LLM behaviour; Proof-of-Guardrail-style attestation only proves a guardrail config was loaded.
- Gas economics favour the bureau verifying quotes off-chain (dcap-qvl / dstack-verifier / NRAS) and publishing the *result* as an EAS attestation (schema: agentId, measurement hash, quote hash, verifier policy version, expiry), rather than every counterparty paying 4-5M gas on Base per verification.

## Key Question 5: MCP and A2A security/trust features relevant to attaching attestations

### Takeaway
MCP authorization is OAuth 2.1 with mandatory RFC 9728 resource metadata and RFC 8707 resource indicators; the 2025-11-25 revision introduced Client ID Metadata Documents and the 2026-07-28 revision deprecated RFC 7591 dynamic client registration in favour of them, added issuer validation (RFC 9207), and made the protocol stateless — none of these carry attestation payloads, so agent attestations would ride as a separate claim/credential or in the MCP registry metadata (which is unsigned). A2A has signed Agent Cards (detached JWS over an RFC 8785-canonicalised card) per multiple secondary sources, but the primary spec text was unreachable.

### Cited Findings

**MCP authorization spec**
- Spec revision directories in the repo: 2024-11-05, 2025-03-26, 2025-06-18, 2025-11-25, 2026-07-28, draft — [modelcontextprotocol spec tree](https://github.com/modelcontextprotocol/modelcontextprotocol/tree/main/docs/specification)
- 2025-06-18: MCP server becomes an OAuth 2.1 resource server; RFC 9728 Protected Resource Metadata for AS discovery; RFC 8707 resource indicators required; "MCP servers MUST NOT accept or transit any other tokens"; 401/403/400 semantics — [Aaron Parecki, "MCP spec" (2025-06-18)](https://aaronparecki.com/2025/06/18/10/mcp-spec); [modelcontextprotocol.io 2025-06-18 authorization](https://modelcontextprotocol.io/specification/2025-06-18/basic/authorization)
- 2025-11-25 authorization: authorization is optional and applies to HTTP transports; "MUST implement OAuth 2.1"; MCP servers must publish RFC 9728 metadata and clients must support both WWW-Authenticate and well-known discovery; clients must support RFC 8414 and OIDC Discovery; "MCP clients MUST send this [resource] parameter regardless of whether authorization servers support it"; PKCE S256 required and "MCP clients MUST verify PKCE support before proceeding"; client registration priority: pre-registered → Client ID Metadata Documents (client_id is an HTTPS URL; advertised via `client_id_metadata_document_supported`) → RFC 7591 DCR (fallback) → prompt user; "MCP servers MUST only accept tokens specifically intended for themselves"; "The MCP server MUST NOT pass through the token it received from the MCP client"; tokens only in Authorization header, never query string; optional extensions live in a separate repo — [2025-11-25 authorization.mdx](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/docs/specification/2025-11-25/basic/authorization.mdx)
- 2026-07-28 changelog: stateless protocol (no `Mcp-Session-Id`, no `initialize`; versions/capabilities in `_meta`; new `server/discover`); `subscriptions/listen`; removal of `ping`, `logging/setLevel`, roots notifications; tasks moved to an extension; `InputRequiredResult` and required `resultType`; SSE resumability removed. Authorization: issuer validation (SEP-2468, RFC 9207 `iss` — clients MUST validate when present); credential binding by issuer (SEP-2352); DCR `application_type` (SEP-837); "RFC 7591 is deprecated as a registration mechanism in favor of Client ID Metadata Documents (PR #2858)"; deprecations of Roots, Sampling, Logging, HTTP+SSE transport, with a minimum twelve-month deprecation window (SEP-2596); changelog does not mention enterprise-managed authorization or cross-app access — [2026-07-28 changelog.mdx](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/docs/specification/2026-07-28/changelog.mdx); 2026-07-28 authorization folder contains `authorization-server-discovery.mdx`, `client-registration.mdx`, `index.mdx`, `security-considerations.mdx` — [authorization dir](https://github.com/modelcontextprotocol/modelcontextprotocol/tree/main/docs/specification/2026-07-28/basic/authorization)

**MCP Registry**
- Official registry launched in preview 2025-09-08 at registry.modelcontextprotocol.io ("breaking changes or data resets may occur"); API freeze v0.1 on 2025-10-24; publishing via `mcp-publisher` CLI with namespace ownership proven by GitHub OAuth, GitHub OIDC, DNS or HTTP challenge; the README "does not mention cryptographic signing of registry entries" — [modelcontextprotocol/registry](https://github.com/modelcontextprotocol/registry); [registry preview blog](https://blog.modelcontextprotocol.io/posts/2025-09-08-mcp-registry-preview/)

**A2A agent card signatures**
- A2A lets servers attach JWS signatures to the published Agent Card; signature is a JWS (RFC 7515) computed over the JSON-canonicalised card (RFC 8785); each entry in the optional `signatures` array is a detached JWS over the card excluding `signatures`; verifiers check against the issuer's public key from a registry or `x5c` chain; one source says A2A v1.0 reached stable in April 2026 and added signed agent cards (all secondary) — [Tyk A2A security guide](https://tyk.io/learning-center/a2a-security-the-developers-complete-guide/); [Tyk A2A architecture](https://tyk.io/learning-center/a2a-protocol-architecture-and-technical-specification/); [TowardsAI article on v1.0 signing](https://pub.towardsai.net/before-your-agent-trusts-a-stranger-how-a2a-v1-0-signs-agent-cards-aa92c6c7e84b); [AG2 card signing docs](https://docs.ag2.ai/docs/user-guide/a2a/card_signing/); Ruby gem type `A2A::AgentCardSignature` — [rubydoc](https://rubydoc.info/gems/a2a/A2A/AgentCardSignature); Bernstein example uses Ed25519 keys with a published JWKS — [bernstein docs](https://bernstein.readthedocs.io/en/latest/architecture/a2a/)
- A2A discovery: cards served at `https://{agent-server-domain}/.well-known/agent-card.json` (RFC 8615); curated registries supported but "the current A2A specification does not define a standard registry API"; recommends out-of-band dynamic credentials over static secrets in the card; extended cards gated by auth — [agent-discovery.md](https://github.com/a2aproject/A2A/blob/main/docs/topics/agent-discovery.md)
- A2A enterprise doc: relies on HTTP headers with OAuth2/OIDC, API keys, bearer tokens; TLS 1.2+; 401 with WWW-Authenticate / 403 semantics; the card's `security` field declares supported schemes — [enterprise-ready.md](https://github.com/a2aproject/A2A/blob/main/docs/topics/enterprise-ready.md)
- ERC-8004 registration files reference `A2A` and `MCP` endpoints under `services` and can declare `supportedTrust: ["tee-attestation", ...]` — [erc-8004.md](https://github.com/ethereum/ERCs/blob/master/ERCS/erc-8004.md)

### Inferences
- Neither MCP nor A2A carries a native "attestation" object. The cleanest attachment points are: (a) the A2A Agent Card (signed) with a field referencing the bureau's EAS attestation UID(s) and the ERC-8004 agentId, so the card signature key, the attested TEE key and the on-chain agentWallet can be cross-checked; (b) an OAuth access token issued by an AS that consults bureau attestations before minting (MCP's token-audience rules make this a per-server trust decision); (c) ERC-8004's registration file `services`/`supportedTrust` for discovery. The MCP registry cannot serve as a trust root because entries are only namespace-verified, not signed.
- Because MCP 2026-07-28 moved to Client ID Metadata Documents (HTTPS-URL client_ids), a bureau could bind an MCP client identity to an attestation by attesting the CIMD URL/hash, giving authorization servers a lookup key.

### Gaps
- The A2A specification text (a2a-protocol.org and the GitHub `specification.md`, which was truncated to a header) was not readable, so the exact `AgentCardSignature` field names (`protected`, `signature`, `header`), the JWS algorithms allowed, and the "v1.0 stable April 2026" date are unverified against the primary spec.
- The 2026-07-28 authorization `index.mdx` / `client-registration.mdx` / `security-considerations.mdx` bodies were not fetched; details above come from the changelog and the 2025-11-25 text.
- Whether the MCP authorization extensions repo includes an "enterprise-managed authorization" / cross-app access (identity assertion) extension could not be confirmed (secondary sources mention it; the changelog does not).
- MCP registry GA status after October 2025 was not confirmed (secondary sources cite ~9,652 listings by April 2026).
