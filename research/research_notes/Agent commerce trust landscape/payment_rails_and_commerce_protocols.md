## 1. x402 (Coinbase → x402 Foundation): mechanics, chains, adoption numbers, governance, payer identity

### Takeaway
x402 is a bare HTTP-402 settlement rail: the only payer identifier in the spec is a wallet address, there is no identity verification, dispute, refund or reputation layer, and the only "trust" statement is a *trust-minimizing* principle about facilitators not moving funds beyond client intent. The headline adoption claims in the design doc ("160M+ payments, ~129M on Base, $42M volume by mid-2026") are in the right order of magnitude but could not be matched to any primary figure; the best-sourced number is Chainalysis's ">138M cumulative transactions on Base by Q3 2026," and independent analysts (TRM Labs) estimate only 0.6–7.5% of that is genuinely agent-driven.

### Cited Findings

**Protocol mechanics (primary, x402 Foundation spec v2)**
- Protocol Version 2 (v2.0) is dated 2025-12-09 in the spec's version history; `x402Version` must be `2`. Headers: `PAYMENT-REQUIRED` (base64 `PaymentRequired` on the 402 response), `PAYMENT-SIGNATURE` (client's `PaymentPayload`), `PAYMENT-RESPONSE` (base64 settlement result on 200), and `EXTENSION-RESPONSES` (facilitator sidechannel, not forwarded to buyers). — [x402 spec v2](https://github.com/x402-foundation/x402/blob/main/specs/x402-specification-v2.md); [x402-foundation/x402 README](https://github.com/x402-foundation/x402)
- The `X-PAYMENT` header named in the design doc does **not** appear in the v2 spec or README; the repo keeps a separate `x402-specification-v1.md` and `transports-v1/` folder, so `X-PAYMENT` is a v1 artifact (v1 file exists but its text was not fetched in this session). — [specs folder listing](https://github.com/x402-foundation/x402/tree/main/specs)
- `PaymentRequired.accepts[]` entries carry `scheme`, `network`, `amount`, `asset`, `payTo`, `maxTimeoutSeconds`, optional `extra`; `resource` carries `url` plus optional `description`, `mimeType`, `serviceName`, `tags`, `iconUrl`. `PaymentPayload` for the EVM `exact` scheme carries a `signature` and an EIP-3009 `authorization` (`from`, `to`, `value`, `validAfter`, `validBefore`, `nonce`). — [x402 spec v2](https://github.com/x402-foundation/x402/blob/main/specs/x402-specification-v2.md)
- Facilitator endpoints: `POST /verify` (read-only, "MUST NOT commit payment state or write onchain state"; returns `isValid`, optional `invalidReason`, `payer`), `POST /settle` (broadcasts; returns `success`, `transaction`, `network`, optional `payer`), `GET /supported` (`kinds`, `extensions`, `signers`). Flows: `authorization` (verify → resource → settle), `upfront` (settle → resource), `escrow` (settle → resource → settle). Resource servers may self-verify/self-settle instead of using a facilitator. — [x402 spec v2](https://github.com/x402-foundation/x402/blob/main/specs/x402-specification-v2.md); [README](https://github.com/x402-foundation/x402)
- The README explicitly warns not to assume the public x402.org facilitator is the default for mainnet EVM routes; options are a production facilitator provider, self-hosting, or self-facilitating. — [README](https://github.com/x402-foundation/x402)
- Networks use CAIP-2 identifiers (`eip155:8453` Base, `eip155:84532` Base Sepolia, `eip155:43114` Avalanche, `solana:` mainnet/devnet); non-blockchain networks are "encouraged" to use CAIP-2 too (examples `ach:us`, `sepa:eu`). Reference SDK packages exist for EVM, SVM (Solana), AVM (Algorand), Aptos, Casper, Stellar, TVM (Tron), Hedera and Keeta. The protocol is described as "network, token, and currency agnostic" with fiat networks possible later. — [x402 spec v2](https://github.com/x402-foundation/x402/blob/main/specs/x402-specification-v2.md); [README](https://github.com/x402-foundation/x402)
- Schemes: `exact`, `upto` (amount = max authorized at verify time; settled amount may be lower), `batch-settlement` (escrow + off-chain vouchers redeemed in batches), `auth-capture`. — [x402 spec v2](https://github.com/x402-foundation/x402/blob/main/specs/x402-specification-v2.md); [README](https://github.com/x402-foundation/x402)
- `coinbase/x402` is now described as a *development fork*; the canonical repository moved to the `x402-foundation` GitHub org (≈6.7k stars, ≈1,300 commits as of fetch). — [coinbase/x402](https://github.com/coinbase/x402); [x402-foundation/x402](https://github.com/x402-foundation/x402)

**Payer identity / trust in the spec (primary)**
- The spec defines no identity verification. The payer appears only as the wallet address in `authorization.from` and as an optional `payer` field in `/verify` and `/settle` responses. KYC, disputes and refunds are not addressed anywhere in the v2 spec. — [x402 spec v2](https://github.com/x402-foundation/x402/blob/main/specs/x402-specification-v2.md)
- The only trust language is the "Trust minimizing" principle: schemes must not allow a facilitator or resource server to move funds except per the client's intentions; facilitators "may be trusted third parties" or hosted by the resource server. Section 10.2 mentions optional integration with Sign-In with Ethereum (SIWE) for authenticated pricing. — [x402 spec v2](https://github.com/x402-foundation/x402/blob/main/specs/x402-specification-v2.md); [README](https://github.com/x402-foundation/x402)
- The `bazaar` discovery extension catalogs x402 endpoints/MCP tools (method, inputs, outputs, `payTo`, scheme, network). Seller metadata (`serviceName`, `tags`, `iconUrl`) is self-declared; the extension carries no reputation, trust or verified-identity data for sellers or buyers. — [bazaar extension](https://github.com/x402-foundation/x402/blob/main/specs/extensions/bazaar.md)

## 2. Google AP2 (Agent Payments Protocol): version, mandates, A2A/x402 relationship, partners, trust and dispute provisions

### Takeaway
AP2 v0.2.0 shipped 2026-04-28 and replaced the launch-era Intent/Cart/Payment mandate trio with **Checkout** and **Payment** mandates (each with "open" and "closed" forms), secured as SD-JWTs. It gives merchants cryptographic proof of user authorization and a "non-repudiable" evidence bundle for disputes, but it explicitly puts dispute resolution, agent-to-agent delegation and how a merchant decides to trust a given shopping agent out of scope — the only hook is a "trust list of Agent Providers."

### Cited Findings
- CHANGELOG: v0.1.0 on 2025-09-16 ("Create Agent Payments Protocol (AP2)"); **v0.2.0 on 2026-04-28** ("Release of V2"). Repo is Apache-2.0, ≈3.2k stars. — [AP2 CHANGELOG](https://github.com/google-agentic-commerce/AP2/blob/main/CHANGELOG.md); [AP2 repo](https://github.com/google-agentic-commerce/AP2)
- The v0.2 spec is titled "Agentic Payment Protocol (v0.2)" and defines two mandate types: a **Checkout Mandate** ("designed to provide the Merchant cryptographic proof" that the Shopping Agent may buy the assembled Checkout, answered by a Checkout Receipt) and a **Payment Mandate** ("designed to provide the Credential Provider, Network, and Merchant Payment Processor cryptographic proof" that the agent may pay for that Checkout, answered by a Payment Receipt). "Intent" is not a mandate; the Trusted Surface role obtains user consent "for an Intent before creating a user-signed Mandate." — [AP2 specification](https://github.com/google-agentic-commerce/AP2/blob/main/docs/ap2/specification.md)
- Autonomous (human-not-present) mode uses **open** mandates (user-signed constraints) and **closed** mandates (bound to one transaction, "signed by an Agent key"). Agent-facing open mandates "MUST include the agent's public key as a `cnf` claim." `vct` claims carry versions such as `mandate.payment.1` and `mandate.checkout.open.1`. — [AP2 specification](https://github.com/google-agentic-commerce/AP2/blob/main/docs/ap2/specification.md)
- Credential format: "AP2 specifies the use of `SD-JWT`s for securing the Payment and Checkout Mandates"; checkout JWTs must use a non-deterministic signature scheme "(e.g., ECDSA)"; other verifiable digital credentials are allowed. — [AP2 specification](https://github.com/google-agentic-commerce/AP2/blob/main/docs/ap2/specification.md)
- Roles: Shopping Agent, Credential Provider ("verifying that this Agent is authorized to access this Payment Credential"), Merchant, Merchant Payment Processor, Trusted Surface ("a UI surface that is trusted to get informed user consent"). — [AP2 specification](https://github.com/google-agentic-commerce/AP2/blob/main/docs/ap2/specification.md)
- Trust in the agent key: "Trust in this key is provided by open Mandates that are signed by the User or a trust list of Agent Providers." The spec does not describe how a Merchant decides whether to trust a Shopping Agent beyond this. — [AP2 specification](https://github.com/google-agentic-commerce/AP2/blob/main/docs/ap2/specification.md)
- Dispute Evidence: mandates and receipts "can be brought together to provide a non-repudiable picture of the transaction," but dispute "retention, and retrieval requirements are outside the scope of this specification." Also out of scope: commerce-protocol details, how mandate content is assembled, and agent-to-agent delegation ("This is outside the scope of the current specification."). — [AP2 specification](https://github.com/google-agentic-commerce/AP2/blob/main/docs/ap2/specification.md)
- "AP2 is agnostic to the particular payment instrument used"; new instruments are added by defining a unique `type`. — [AP2 specification](https://github.com/google-agentic-commerce/AP2/blob/main/docs/ap2/specification.md)
- Launch: Google announced AP2 on 2025-09-16 with "more than 60 partners"; it supports cards, stablecoins and real-time bank transfers. The **A2A x402 extension** was built with Coinbase, the Ethereum Foundation and MetaMask to add stablecoin/crypto payments. (Secondary press.) — [crypto.news](https://crypto.news/google-taps-crypto-giants-on-ai-payment-protocol-extension/); [Decrypt](https://decrypt.co/339752/google-reveals-ai-agent-payments-protocol-coinbase-ethereum-foundation?amp=1)
- The `google-agentic-commerce/a2a-x402` repo (spec v0.1, Apache-2.0, ≈565 stars) defines the A2A flow: merchant agent replies `payment-required` → client agent signs and returns `payment-submitted` → merchant verifies, settles on-chain and returns `payment-completed` with the service. It names no partners and makes no identity or trust statements. — [a2a-x402 repo](https://github.com/google-agentic-commerce/a2a-x402)
- The Ethereum Foundation is finalizing ERC-8004 (agent discovery/verification) alongside the x402 extension. — [Decrypt](https://decrypt.co/339752/google-reveals-ai-agent-payments-protocol-coinbase-ethereum-foundation?amp=1)
- Secondary claim: Google contributed AP2 to the **FIDO Alliance** in April 2026 for a community standards process, and AP2 is "explicitly compatible" with UCP. — [MintMCP](https://www.mintmcp.com/blog/ap2-agent-payments-protocol) (secondary; not confirmed in the AP2 repo)
- UCP's README lists "AP2 mandates and verifiable credentials" as a supported security pattern. — [UCP repo](https://github.com/Universal-Commerce-Protocol/ucp)

### Inferences
- AP2 solves *authorization provenance* (did the human authorize this agent to buy this cart?) rather than *counterparty trust*. The merchant still has no protocol-native way to assess the agent provider beyond a self-chosen trust list — which is exactly the slot a neutral bureau could populate.
- Many explainers (and likely the design doc) still describe Intent/Cart/Payment mandates; that model is v0.1. The v0.2 "open mandate" is the functional successor of the Intent Mandate.

### Gaps
- Could not fetch ap2-protocol.org or the Google Cloud launch blog; the 60+ partner list and the FIDO Alliance contribution are secondary-only.
- The AP2 README/CHANGELOG contain no text on A2A/MCP/x402 relationships; those come from the separate a2a-x402 repo and press.

## 3. Visa Trusted Agent Protocol (TAP) and Visa Intelligent Commerce: recognition mechanism, status, partners, what merchants receive, vetting/scoring

### Takeaway
TAP recognizes agents by RFC 9421 HTTP Message Signatures verified against a Visa-run public-key Agent Registry; merchants receive a verified-agent signal, an operation-bound intent signal (browse vs pay), and optionally consumer identifiers such as PARs. It is binary (verified or not) — the public spec defines no agent scoring, trust tiers, dispute process or liability allocation — and as of late 2025 Visa described it as pilots producing "hundreds of controlled, real-world" transactions with mainstream adoption targeted for 2026.

### Cited Findings
- Visa announced TAP on 2025-10-14 ("Visa Introduces Trusted Agent Protocol: An Ecosystem-Led Framework for AI Commerce"); Cloudflare co-developed it on the Web Bot Auth foundation. Twelve launch partners reported: Adyen, Ant International, Checkout.com, Coinbase, CyberSource, Elavon, Fiserv, Microsoft, Nuvei, Shopify, Stripe, Worldpay. (Secondary summaries of the Visa release.) — [Visa IR release](https://investor.visa.com/news/news-details/2025/Visa-Introduces-Trusted-Agent-Protocol-An-Ecosystem-Led-Framework-for-AI-Commerce/default.aspx); [Visa Perspectives](https://corporate.visa.com/en/sites/visa-perspectives/newsroom/visa-unveils-trusted-agent-protocol-for-ai-commerce.html); [Digital Transactions](https://www.digitaltransactions.net/visa-launches-trusted-agent-an-agentic-commerce-protocol/)
- Mechanism (primary, Visa GitHub sample implementation): components are a TAP Agent that generates RFC 9421 signatures, a CDN Proxy that verifies them, an **Agent Registry** ("Public key registry service for agent verification" that also manages agent metadata), and the Merchant. Signatures include timestamps, a session identifier, a key identifier and an algorithm identifier, and are bound to the merchant's domain and the operation (browsing or payment). — [visa/trusted-agent-protocol](https://github.com/visa/trusted-agent-protocol); [README](https://github.com/visa/trusted-agent-protocol/blob/main/README.md)
- What merchants receive: (a) agent identity — a verified signature marking the agent "legitimate and credentialed"; (b) consumer intent — confirmation the agent is authorized for a specific action; (c) with consumer consent, query-parameter identifiers: verifiable consumer identifiers, Payment Account References (PARs) for cards on file, loyalty numbers, emails, phone numbers. — [visa/trusted-agent-protocol](https://github.com/visa/trusted-agent-protocol)
- The repo does not describe how agents get into the registry (issuance, rotation, revocation), lists no version or release, and has 6 commits on main / 213 stars; it is a sample, not a production standard. Trust is binary; no scoring, trust levels, dispute process or liability text. It says only that TAP "can reduce fraud and minimize chargebacks." — [visa/trusted-agent-protocol](https://github.com/visa/trusted-agent-protocol)
- Secondary spec details (Visa Developer page, unreachable): two signature tags `agent-browser-auth` and `agent-payer-auth`; covered fields `@authority`, `@path`, `created`, `expires`, `keyid`, `alg`, `nonce`, `tag`; Ed25519 keys; 8-minute validity window; keys published at a `.well-known/jwks` endpoint; key discovery/caching and nonce replay tracking are merchant responsibilities. — [Visa Developer spec page](https://developer.visa.com/capabilities/trusted-agent-protocol/trusted-agent-protocol-specifications/); [eco.com TAP explainer](https://eco.com/support/en/articles/14845482-visa-trusted-agent-protocol-tap-explained); [Oscilar](https://oscilar.com/blog/visatap)
- Status/scale (Visa's own late-2025 release): >100 partners, >30 building in the Visa Intelligent Commerce sandbox, >20 agents or agent enablers integrating directly, and "hundreds of controlled, real-world agent-initiated transactions," framed as "setting the stage for mainstream adoption in 2026." — [Visa IR release](https://investor.visa.com/news/news-details/2025/Visa-and-Partners-Complete-Secure-AI-Transactions-Setting-the-Stage-for-Mainstream-Adoption-in-2026/default.aspx)
- Visa said it is aligning TAP with OpenAI's ACP and Coinbase's x402. — [Digital Commerce 360](https://www.digitalcommerce360.com/2025/10/16/visa-mastercard-both-launch-agentic-ai-payments-tools/)
- Akamai joined TAP, adding edge behavioral intelligence, user recognition and bot/abuse protection to "strengthen the agent-intent signal." — [Akamai press release](https://www.akamai.com/newsroom/press-release/akamai-and-visa-join-forces-to-secure-the-next-era-of-agentic-commerce)
- Secondary claim: Visa rules effective **2026-04-18** require agentic transactions to use network tokens bound to a registered agent. Not confirmed in any Visa document reachable here. — [eco.com KYA article](https://eco.com/support/en/articles/14846277-know-your-agent-kya-identity-for-agent-payments)
- Visa and Mastercard both launched agentic-AI risk tools (American Banker, 2026; page unreachable, details unknown). — [American Banker](https://www.americanbanker.com/payments/news/mastercard-visa-launch-agentic-ai-risk-tools)

### Inferences
- TAP's Agent Registry is a gatekeeping allow-list operated by Visa: it answers "is this a Visa-registered agent?" not "how has this agent behaved?" Behavioral signal is being bolted on by partners (Akamai, Cloudflare) rather than defined in the protocol.
- Because TAP binds consumer identifiers (PAR, email) to the request, it covers *consumer* recognition well and *agent-operator* vetting thinly; nothing in the public material scores either the agent or the merchant.

### Gaps
- Visa's developer portal and IR pages could not be fetched; the April 2026 token-binding rule and current 2026 live-merchant counts are unverified.
- No source found giving the number of agents registered in the TAP directory.

## 4. Mastercard Agent Pay / Agentic Tokens: mechanics, status, partners, trust features

### Takeaway
Agent Pay issues per-agent "Agentic Tokens" through Mastercard's existing tokenization service, scoped by agent, merchant and spend rules, and — unlike x402 or AP2 — Mastercard positions explicit "Know Your Agent" vetting and a network-side **agent detection / trust score** (built with Skyfire KYA identity plus intent, behavioral and fraud signals) as part of the offering. As of September–October 2026 the trust-intelligence services are in U.S. testing, the European end-to-end pilot (Santander) is explicitly "not a commercial rollout," and the scoring is an issuer-authorization aid rather than a merchant-facing counterparty rating.

### Cited Findings
- Agent Pay was unveiled in April 2025 and rolled out to all U.S. cardholders by November 2025. (Secondary.) — [FintechSpecs](https://fintechspecs.com/blog/mastercard-agent-pay-trust-intelligence-skyfire-kya-2026/); [eco.com Agent Pay](https://eco.com/support/en/articles/15192001-what-is-mastercard-agent-pay-ai-agent-commerce-protocol-in-2026)
- Mechanics: Agentic Tokens are issued via Mastercard's tokenization service; each is tied to one agent and its permitted merchants and spending rules; agents must pass KYA vetting before token access. (Secondary.) — [eco.com Agent Pay](https://eco.com/support/en/articles/15192001-what-is-mastercard-agent-pay-ai-agent-commerce-protocol-in-2026); [Stellagent](https://stellagent.ai/insights/mastercard-agent-pay-agentic-tokens); [eco.com KYA](https://eco.com/support/en/articles/14846277-know-your-agent-kya-identity-for-agent-payments)

## 5. ACP (OpenAI/Stripe) and Shared Payment Tokens; Google UCP; Shopify; PayPal; Amazon "Buy for Me"; Perplexity — who vets whom, dispute handling

### Takeaway
In every card-based checkout protocol the pattern is the same: the *platform* (OpenAI, Google, Microsoft, Perplexity) vets and onboards merchants, the *merchant* stays merchant-of-record and absorbs refunds and chargebacks, and the *agent* is trusted because it is the platform's own first-party agent authenticated by API keys/signatures — there is no third-party or portable vetting of agents, and no protocol-level dispute mechanism. The design-doc claim that UCP provides checkout for "hundreds of thousands" of merchants was not corroborated: UCP checkout is in limited early access for eligible merchants in the US, Canada and Australia.

## 7. Public statements on reputation, KYA ("know your agent") and counterparty scoring: in or out of scope?

### Takeaway
Only the card networks have said anything explicit: Mastercard (with Skyfire) and Visa (TAP registry) treat KYA as *their* function, and in September 2026 Visa, Mastercard and Ant International began a cross-network KYA interoperability framework (operator linkage, shared certification, ongoing monitoring) while keeping decisioning network-specific. x402, AP2, ACP and UCP are silent or explicitly out-of-scope on agent reputation; the only open reputation primitive in the ecosystem is ERC-8004 (still Draft), which self-describes its Sybil weakness.

### Cited Findings
- Visa, Mastercard and Ant International announced (September 2026) the "first cross-network Know Your Agent framework": linking agents to validated operators, shared certification requirements, and monitoring transactions over time; each network keeps its own verification and decisioning processes. Status: beginning/announced. — [PYMNTS](https://www.pymnts.com/cybersecurity/2026/visa-mastercard-team-with-ant-know-your-agent-framework); [Yahoo Finance](https://finance.yahoo.com/technology/ai/articles/visa-mastercard-ant-international-build-111358124.html); [SuperpowerDaily](https://superpowerdaily.com/posts/ant-international-visa-and-mastercard-begin-shared-rules-for-ai-payment-agents)
- Mastercard's September 2026 trust-and-intelligence services (Skyfire KYA + agent detection score, U.S. testing) — see Section 4. — [Mastercard press release](https://www.mastercard.com/us/en/news-and-trends/press/2026/september/new-trust-and-intelligence-services.html)
- A June 2026 opinion piece argues the networks do not need a third-party KYA layer because their role as trust certifiers already fills it. — [StarPoint](https://blog.starpointllp.com/2026/06/is-know-your-agent-kya-really-necessary/)
- x402 v2 spec: no identity, KYC, dispute or reputation provisions; `bazaar` carries only self-declared seller metadata. — [x402 spec v2](https://github.com/x402-foundation/x402/blob/main/specs/x402-specification-v2.md); [bazaar](https://github.com/x402-foundation/x402/blob/main/specs/extensions/bazaar.md)
- AP2 v0.2: trust in an agent key comes from user-signed open mandates "or a trust list of Agent Providers"; dispute retention/retrieval and agent-to-agent delegation are out of scope. — [AP2 specification](https://github.com/google-agentic-commerce/AP2/blob/main/docs/ap2/specification.md)
- ACP and UCP public repos: no reputation, agent-vetting or dispute text. — [ACP repo](https://github.com/agentic-commerce-protocol/agentic-commerce-protocol); [UCP repo](https://github.com/Universal-Commerce-Protocol/ucp)
- ERC-8004 "Trustless Agents" (Draft, created 2025-08-13; authors from MetaMask, Ethereum Foundation, Google (Jordan Ellis) and Coinbase (Erik Reppel)) defines Identity (ERC-721 agent IDs with agentURI/agentWallet), Reputation (`giveFeedback` with signed value, tags, off-chain file + hash; revocable; submitter cannot be the agent owner) and Validation (validator scores 0–100) registries. Payments are out of scope, but the feedback file has a `proofOfPayment` field for x402 proof. Security section: Sybil attacks "are possible, so fake agents can inflate reputation"; the spec expects reviewer filtering and external reputation systems to address this. — [ERC-8004](https://github.com/ethereum/ERCs/blob/master/ERCS/erc-8004.md)
- The Ethereum Foundation's AI lead said the x402 extension to AP2 eases developer experience while EF finalizes ERC-8004 for agents to "discover, verify, and transact with each other." — [Decrypt](https://decrypt.co/339752/google-reveals-ai-agent-payments-protocol-coinbase-ethereum-foundation?amp=1)

### Inferences
- Coverage map for a buyer-agent ↔ merchant-agent trust decision, by rail: x402 — none (address only); AP2 — authorization proof + opaque "trust list"; TAP — binary Visa registry membership; Agent Pay — issuer-side score, not merchant-portable; ACP/UCP — platform gatekeeping, no agent-level signal; ERC-8004 — open feedback ledger, Sybil-prone, Draft. Nothing public today offers a neutral, cross-rail, bidirectional (agent *and* merchant) history with dispute outcomes.
- Natural plug-in points for a neutral bureau, given the interfaces above: (1) an x402 extension (the spec's `extensions` mechanism and the facilitator's `/verify` response, which already returns `payer`) to attach a score or attestation; (2) a signer on AP2's "trust list of Agent Providers"; (3) a data source into TAP's Agent Registry metadata or Mastercard's agent-detection inputs (as Skyfire is); (4) an ERC-8004 Validation-registry validator or reputation aggregator; (5) a Radar-style risk signal travelling with Stripe SPTs.

### Gaps
- No primary Visa/Mastercard/Ant document on the cross-network KYA framework was reachable; its certification criteria, timeline and whether it includes any numeric scoring are unknown.
- No statement found from the x402 Foundation, OpenAI/Stripe (ACP) or Google (UCP/AP2) explicitly declaring agent reputation in or out of scope beyond spec silence.
- Web Bot Auth (IETF draft) status and its relation to TAP key discovery were not verified from a primary source.
